Архитектурное проектирование и регламент разработки автономного Bluetooth-мессенджера (Android 16)
Разработка мобильного приложения для обмена текстовыми сообщениями по протоколу Bluetooth без использования интернет-инфраструктуры представляет собой многоуровневую инженерную задачу. В условиях жестких регламентов оценки индивидуального вклада и качества кода создание Minimum Viable Product (MVP) требует исключительной архитектурной дисциплины. Стратегия реализации базируется на строгом соблюдении паттерна Model-View-ViewModel (MVVM), где бизнес-логика полностью изолирована от слоя представления [1, 1].
Настоящий отчет представляет собой исчерпывающий пошаговый план, состоящий из 51 этапа разработки (соответствующих 51 коммиту в системе контроля версий). План детализирует процесс интеграции новейших компонентов экосистемы Android (включая Room 3.0, Jetpack Compose 1.11.0 и специфические API операционной системы Android 16), распределение зон ответственности между двумя разработчиками и методику формирования структурированных запросов (промптов) для агентов генеративного искусственного интеллекта (ИИ), таких как интегрированная среда разработки Cursor [1].
Стратегия контроля версий и методология слияния веток
Строгое соблюдение дисциплины работы с Git является фундаментальным требованием для подтверждения индивидуального вклада каждого разработчика [1, 1]. Прямые коммиты в основную ветку разработки (main) категорически запрещены до финального этапа интеграции продукта.
Архитектура проекта и распределение задач требуют физического и логического разделения на две изолированные зоны:
Первый разработчик (Data & Network Engineer) несет ответственность за проектирование реляционных моделей, управление состоянием локальной базы данных и реализацию низкоуровневого сетевого взаимодействия [2]. Все работы данного специалиста выполняются в тематических ветках с префиксами feature/data-* или feature/network-*. Данный участник обязан выполнить ровно 25 индивидуальных коммитов [2].
Второй разработчик (UI/UX & UI-Logic Developer) концентрирует усилия на слое представления, визуальной отрисовке состояний и обработке пользовательского ввода через классы ViewModel [2]. Работы ведутся в ветках с префиксом feature/ui-*. Этот участник также выполняет ровно 25 индивидуальных коммитов [2].
Для предотвращения масштабных конфликтов слияния (Merge Conflicts) и обеспечения непрерывной интеграции устанавливается следующий регламент синхронизации кодовой базы.
Абсолютным правилом является отключение функции Squash-коммитов при слиянии Pull Request. Оценочная комиссия анализирует количество и качество индивидуальных транзакций кода, поэтому все 50 промежуточных коммитов должны сохраниться в первозданном виде с сохранением временных меток и авторства [2].
Стандарты промпт-инжиниринга для ИИ-Агентов
Генерация кода с использованием таких инструментов, как Cursor IDE, требует глубокого понимания принципов работы языковых моделей с контекстом проекта [1]. Использование размытых формулировок неизбежно приводит к генерации устаревшего кода (галлюцинациям), несовместимого с экосистемой Android 16. Эффективные промпты для ИИ-агента всегда включают три структурных элемента: четкое описание контекста и технологического стека, точную алгоритмическую задачу и строгие ограничительные рамки (Constraints), запрещающие использование устаревших паттернов [1, 3].
Каждый из описанных ниже 50 шагов разработки сопровождается детализированным промптом, который загружается в окно диалога ИИ-помощника для автоматической генерации или рефакторинга кода.
Детализированный план: Фаза 1 — Инфраструктура и База Данных
Данный блок закладывает фундамент архитектуры приложения, конфигурирует новейшие библиотеки по состоянию на 2026 год и инициализирует работу системы хранения данных.
Шаг 1: Инициализация проекта и конфигурация среды сборки
В рамках первого коммита первый участник (Data Engineer) формирует базовую структуру Gradle-проекта. Осуществляется отказ от устаревшего инструмента Java Annotation Processing (KAPT) в пользу нативного Kotlin Symbol Processing (KSP) [4, 5]. Внедряется единая спецификация Jetpack Compose BOM версии 2026.04.01 [6]. Целевая платформа устанавливается на уровень API 36 (Android 16).
Промпт для ИИ-агента включает передачу контекста о сборке современного Android-проекта. Агенту формулируется задача сгенерировать конфигурационный файл build.gradle.kts уровня модуля. В качестве строгих ограничений указывается необходимость использования исключительно Kotlin DSL, обязательное добавление плагина KSP версии 2.3.7 [7] и подключение зависимостей androidx.room3:room3-runtime:3.0.0-alpha03 [8] и androidx.sqlite:sqlite-bundled [8].
Рабочая ветка: feature/data-init (создается от ветки develop [2])
Описание коммита: chore(build): setup gradle with KSP, Room 3.0 and Compose BOM 2026.04.01
Шаг 2: Внедрение архитектуры Edge-to-Edge
Второй участник (UI Developer) начинает работу с графической оболочкой. В операционной системе Android 16 атрибут windowOptOutEdgeToEdgeEnforcement полностью отключен, что делает отрисовку пользовательского интерфейса под системными панелями навигации и статус-баром строго обязательной [2, 9].
Промпт для ИИ-агента задает контекст создания базовой темы Material Design 3. Задачей является формирование файла Theme.kt и конфигурация корневой функции MainActivity. Агенту строго запрещается использование устаревшей библиотеки Accompanist Systemuicontroller. Инструкция требует обязательного вызова функции enableEdgeToEdge() в методе onCreate и применения модификатора Modifier.systemBarsPadding() для корневого контейнера Jetpack Compose [10, 11].
Рабочая ветка: feature/ui-theme (создается от ветки develop [2])
Описание коммита: feat(ui): implement Edge-to-Edge architecture and Material 3 theme
Шаг 3: Проектирование реляционных сущностей Room 3.0
Первый участник возвращается к слою данных для описания структуры таблиц. База данных должна надежно хранить историю сообщений и метаданные сопряженных устройств. Учитывая будущую интеграцию шифрования, сущность сообщения должна содержать поля для хранения вектора инициализации и зашифрованной полезной нагрузки [12].
Промпт для ИИ-агента описывает контекст использования библиотеки Room 3.0. Задачей выступает разработка класса данных MessageEntity, аннотированного как @Entity. В ограничениях указывается необходимость использования пакета androidx.room3 [8] и создания полей: уникальный идентификатор (Primary Key), MAC-адрес устройства, массив байтов encryptedPayload, массив байтов iv (вектор инициализации) и временная метка timestamp.
Рабочая ветка: feature/data-db-models (создается от ветки develop [2])
Описание коммита: feat(db): create MessageEntity with AES encryption fields
Шаг 4: Настройка типобезопасной системы навигации
Второй участник настраивает маршрутизацию между экранами приложения. Использование строковых констант для навигации признано устаревшим, поэтому внедряется библиотека androidx.navigation:navigation-compose:2.9.8, обеспечивающая проверку типов на этапе компиляции [2].
Промпт для ИИ-агента устанавливает контекст работы с Navigation Compose 2.9.8 и библиотекой Kotlin Serialization. Перед агентом ставится задача реализовать компонент NavHost, включающий два типобезопасных маршрута: объект DeviceListRoute для экрана поиска и класс данных ChatRoute(val deviceMac: String) для экрана чата. Жестким ограничением является полный отказ от использования строковых маршрутов в пользу сериализуемых классов и объектов Kotlin.
Рабочая ветка: feature/ui-navigation (создается от ветки develop [2])
Описание коммита: feat(nav): configure type-safe navigation with Navigation Compose 2.9.8
Шаг 5: Разработка асинхронных интерфейсов доступа к данным (DAO)
Первый участник проектирует методы взаимодействия с таблицами. Библиотека Room 3.0 функционирует в строгой парадигме Coroutines-first, где все методы доступа к данным обязаны быть асинхронными, что обусловлено переходом на Kotlin Multiplatform [4].
Промпт для ИИ-агента задает контекст архитектуры Room 3.0. Задачей является написание интерфейса MessageDao с набором CRUD-операций. Агенту устанавливаются жесткие ограничения: операция вставки сообщения должна быть помечена модификатором suspend, а метод извлечения истории сообщений по MAC-адресу обязан возвращать реактивный поток Flow<List<MessageEntity>>. Категорически запрещается использование синхронных возвращаемых типов или устаревших классов LiveData.
Рабочая ветка: feature/data-db-dao (создается от ветки develop [2])
Описание коммита: feat(db): implement MessageDao with Coroutines and Flow
Шаг 6: Формирование базового каркаса экранов (Scaffold)
Второй участник подготавливает фундамент для декларативной верстки. Компонент Scaffold предоставляет стандартную структуру с верхней панелью и плавающей кнопкой действия, однако требует аккуратной работы с отступами для поддержки Edge-to-Edge дизайна [9].
Промпт для ИИ-агента устанавливает контекст работы с Jetpack Compose. Задачей является создание пустой функции @Composable DeviceListScreen, обернутой в компонент Scaffold. В качестве ограничения агенту предписывается обязательное использование параметра innerPadding, предоставляемого компонентом Scaffold, который должен быть передан в дочерний контейнер Box через модификатор Modifier.padding(innerPadding) для предотвращения перекрытия контента системными панелями [9].
Рабочая ветка: feature/ui-scaffold (создается от ветки develop [2])
Описание коммита: feat(ui): build DeviceListScreen scaffold with innerPadding support
Шаг 7: Инициализация базы данных с BundledSQLiteDriver
Первый участник настраивает инициализацию Room. Версия 3.0 полностью отказалась от генерации Java-кода и использования рефлексии (Class.newInstance) для инстанцирования БД. Для обеспечения нативной работы и совместимости теперь используется аннотация @ConstructedBy и драйвер BundledSQLiteDriver [8].
Промпт для ИИ-агента передает контекст пространства имен androidx.room3. Агенту поручается создать абстрактный класс AppDatabase и настроить конфигуратор RoomDatabase.Builder. В ограничениях строго указывается необходимость применения аннотации @ConstructedBy(AppDatabaseConstructor::class) над классом базы данных, а при вызове билдера — обязательное использование методов .setDriver(BundledSQLiteDriver()) и .setQueryCoroutineContext(Dispatchers.IO) [8, 13].
Рабочая ветка: feature/data-db-init (создается от ветки develop [2])
Описание коммита: feat(db): initialize Room 3.0 with BundledSQLiteDriver and @ConstructedBy
Шаг 8: Проектирование UI-состояний (StateFlow)
Второй участник проектирует контракт взаимодействия между представлением и бизнес-логикой. Внедряется подход на основе намерений (MVI-подобная архитектура), где каждое состояние экрана описывается строго типизированной иерархией классов.
Промпт для ИИ-агента содержит контекст паттерна MVVM на языке Kotlin. Задача состоит в генерации запечатанного интерфейса (sealed interface) ChatUiState, включающего состояния загрузки, успешного отображения списка сообщений и ошибки, а также интерфейса намерений ChatIntent. Ограничения предписывают, что все состояния должны быть абсолютно неизменяемыми структурами данных (data class или data object).
Рабочая ветка: feature/ui-mvi-state (создается от ветки develop [2])
Описание коммита: feat(ui): define sealed interfaces for ChatUiState and ChatIntent
Шаг 9: Реализация слоя Repository как единого источника истины
Первый участник создает класс репозитория, который абстрагирует источники данных от остальной части приложения. Согласно паттерну Single Source of Truth, этот класс инкапсулирует вызовы DAO и в дальнейшем будет координировать сетевое взаимодействие, отдавая данные исключительно через реактивные потоки [2].
Промпт для ИИ-агента описывает контекст использования Kotlin Coroutines. Задача заключается в написании класса MessageRepositoryImpl, реализующего интерфейс хранилища. Основным ограничением является запрет на прямое инстанцирование зависимостей внутри класса; интерфейс DAO должен передаваться исключительно через конструктор для обеспечения тестируемости кода [2].
Рабочая ветка: feature/data-repository (создается от ветки develop [2])
Описание коммита: feat(data): implement MessageRepositoryImpl as Single Source of Truth
Шаг 10: Интеграция обработки пустых состояний (Empty States)
Второй участник завершает первую фазу разработкой визуальных заглушек. Качественный пользовательский интерфейс обязан элегантно обрабатывать краевые сценарии, такие как полное отсутствие истории переписки или пустой список обнаруженных устройств поблизости [2].
Промпт для ИИ-агента задает контекст декларативной графики Jetpack Compose. Задачей является создание переиспользуемой функции @Composable EmptyStateView, принимающей в качестве параметров иконку и текстовое сообщение. Агенту предписывается выровнять элементы строго по центру экрана и использовать семантические модификаторы для поддержки сервисов доступности (Accessibility).
Рабочая ветка: feature/ui-empty-states (создается от ветки develop [2])
Описание коммита: feat(ui): create EmptyStateView component for edge cases
Фаза 2 — Сетевой слой Bluetooth и управление разрешениями
На этом этапе реализуется ядро беспроводной коммуникации. Особое внимание уделяется глубокой интеграции с аппаратным стеком и соблюдению обновленных политик конфиденциальности Android 16.
Шаг 11: Архитектура логики разрешений Android 16
Первый участник разрабатывает механизм запроса системных привилегий. Если приложение использует классический протокол Bluetooth RFCOMM без вычисления физического местоположения, достаточно запросить BLUETOOTH_CONNECT и BLUETOOTH_SCAN [14]. Однако архитектура должна предусматривать утилитарный класс для их управления.
Промпт для ИИ-агента предоставляет контекст работы с системой разрешений Android 16 (API 36). Агенту ставится задача создать утилитарный класс PermissionManager, возвращающий массивы необходимых разрешений. Ограничения требуют учесть особенности API 31+ (Android 12), где разрешения Bluetooth были отделены от разрешений локации, если не используются BLE-маячки [14].
Рабочая ветка: feature/network-permissions (создается от ветки develop [2])
Описание коммита: feat(network): create PermissionManager for Android 16 Bluetooth permissions
Шаг 12: Пользовательский интерфейс запроса разрешений
Второй участник интегрирует системные диалоги запроса привилегий непосредственно в композицию экрана. Интерфейс должен корректно реагировать на отказ пользователя предоставить доступ к радиомодулю.
Промпт для ИИ-агента содержит контекст работы с побочными эффектами (Side Effects) в Jetpack Compose. Задача заключается в написании функции-обертки PermissionRequester. В качестве строгого ограничения указывается необходимость использования контракта rememberLauncherForActivityResult совместно с ActivityResultContracts.RequestMultiplePermissions, а также логика отображения компонента Snackbar в случае отклонения запроса пользователем.
Рабочая ветка: feature/ui-permissions (создается от ветки develop [2])
Описание коммита: feat(ui): integrate ActivityResultContracts for permission requests
Шаг 13: Сканирование радиоэфира (Bluetooth Discovery)
Первый участник приступает к реализации поиска периферийных устройств. Механизм опирается на инициализацию системного компонента BroadcastReceiver, который перехватывает широковещательные интенты BluetoothDevice.ACTION_FOUND и преобразует их в доменные модели приложения [2].
Промпт для ИИ-агента задает контекст работы с Android Bluetooth API. Задачей выступает реализация функции поиска устройств. Ограничения предписывают использовать callbackFlow для трансформации асинхронных вызовов BroadcastReceiver в непрерывный реактивный поток данных (Flow), а также игнорировать устройства, у которых системное имя равно null, заменяя его на аппаратный MAC-адрес.
Рабочая ветка: feature/network-discovery (создается от ветки develop [2])
Описание коммита: feat(network): implement Bluetooth discovery using BroadcastReceiver and callbackFlow
Шаг 14: Интеграция обнаружения устройств в ViewModel
Второй участник связывает реактивный поток обнаруженных устройств со слоем представления. Это требует трансформации холодного потока в горячий для корректного управления жизненным циклом корутин.
Промпт для ИИ-агента описывает контекст архитектурного компонента ViewModel. Задача заключается в подписке DeviceListViewModel на поток из менеджера Bluetooth. Ключевым ограничением является требование использовать оператор stateIn с политикой SharingStarted.WhileSubscribed(5000), что гарантирует остановку сканирования радиоэфира через 5 секунд после того, как пользователь свернет приложение или перейдет на другой экран, экономя заряд батареи.
Рабочая ветка: feature/ui-device-list-vm (создается от ветки develop [2])
Описание коммита: feat(vm): subscribe DeviceListViewModel to device discovery flow
Шаг 15: Инициализация серверного сокета RFCOMM (Server Socket)
Первый участник разрабатывает процесс ожидания входящих подключений. Классический протокол Bluetooth эмулирует последовательный порт. Одно из устройств должно открыть серверный сокет и перейти в режим прослушивания [2].
Промпт для ИИ-агента задает контекст многопоточного программирования и Java/Kotlin Bluetooth API. Задача — написание класса AcceptThread, который открывает серверный сокет через вызов listenUsingRfcommWithServiceRecord. Ограничения строго требуют запускать данный поток в пуле диспетчеров Dispatchers.IO, корректно обрабатывать исключения IOException и реализовать безопасный метод cancel() для принудительного освобождения ресурсов сокета при необходимости.
Рабочая ветка: feature/network-server-socket (создается от ветки develop [2])
Описание коммита: feat(network): initialize RFCOMM server socket in AcceptThread
Шаг 16: Декларативное представление списка устройств
